Las capas y dónde se rompe la caché

Cada instrucción del Dockerfile produce una capa, y una capa que cambia invalida todas las que vienen después. Mover dos líneas de sitio decide si el segundo build tarda dos segundos o siete.

1. La pila de capas

De abajo hacia arriba, lo que construye la imagen de la aplicación de ejemplo. El vacío es el punto de partida: un sistema de archivos que no existe todavía.

Las capas son inmutables y se comparten entre imágenes que las reutilicen. ¿Qué se sigue de eso?

2. Dos órdenes para el mismo Dockerfile

Dependencias primero

1FROM python:3.12-slim
2WORKDIR /app
3COPY requirements.txt .
4RUN pip install --no-cache-dir -r requirements.txt
5COPY app.py .
6CMD ["python", "app.py"]

Código primero

1FROM python:3.12-slim
2WORKDIR /app
3COPY . /app
4RUN pip install --no-cache-dir -r requirements.txt
5CMD ["python", "app.py"]

Se edita una línea de app.py y se vuelve a construir.

Con dependencias primero, ¿cuántos de los seis pasos salen de la caché?

3. Lo que cuesta la línea mal puesta

Las tres construcciones, medidas: la primera con --no-cache, y las dos segundas tras la misma edición de una línea.

¿Cuántas veces más tarda la segunda construcción con el código arriba?

La regla práctica sale de ahí: lo que cambia poco va arriba, cerca del FROM, y lo que cambia con cada commit va al final. Una línea de app.py cambia el contenido de su capa y de todas las siguientes; con las dependencias arriba, esa cadena empieza en el paso 5, y con COPY . /app arriba empieza en el 3 y arrastra la instalación.

4. Qué invalida la caché

El equipo agrega un RUN apt-get update al final del Dockerfile y nota que el build volvió a tardar lo mismo que antes. ¿Qué pasó?

El antipatrón del segundo apartado es el que se paga todos los días: COPY . /app antes de instalar dependencias reinstala todo en cada cambio de código, y el síntoma es un build que nunca baja de su tiempo completo.
