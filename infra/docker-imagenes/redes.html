Quién alcanza a quién

Tres contenedores, dos de ellos en una red creada a mano y el tercero en la que Docker trae de fábrica. Diga qué contesta cada ping antes de ver la tabla: los dos modos de fallar no son el mismo.

1. Tres contenedores, dos redes

$docker network create red-app
$docker run -d --name db --network red-app alpine sleep 3600
$docker run -d --name api --network red-app alpine sleep 3600
$docker run -d --name fuera alpine sleep 3600

Para cada orden, elija lo que contesta. La dirección 172.19.0.2 es de un contenedor de red-app.

DesdeOrdenQué contestaPor qué
Los dos fallos del contenedor de fuera dicen cosas distintas. Con el nombre, el ping nunca sale: no hay quién traduzca db a una dirección. Con la dirección no hay nada que traducir, y el paquete sale y no llega, porque ese contenedor no está en esa red.

2. Qué hizo posible el ping por nombre

La API se conecta a la base de datos con db:5432. ¿Qué gana esa cadena frente a escribir la dirección?

3. Conectar en caliente

$docker network connect red-app fuera
$docker exec fuera ping -c 1 db
$docker network disconnect red-app fuera

¿Qué contesta ese ping ahora?

4. Qué red pide cada caso

Tres contenedores que tienen que hablar entre sí, un agente que necesita ver los puertos del anfitrión y un proceso que solo hace cuentas con lo que trae adentro.

La red por omisión queda para el contenedor suelto que solo necesita salir a Internet. En cuanto dos servicios se buscan por nombre, va una red propia.
