El ciclo de vida y la parada ordenada

Un contenedor pasa por cuatro estados y solo uno de ellos libera lo que escribió. Recorra la secuencia orden por orden y después mida cuánto tarda en parar un servicio que atiende la señal y uno que la ignora.

1. Orden por orden

Cada botón ejecuta la orden siguiente sobre el mismo contenedor y muestra lo que informa docker ps -a después.

Un contenedor Exited conserva su capa escribible y sus registros: por eso se puede leer docker logs de algo que ya terminó. Solo docker rm los borra, y entonces la consulta devuelve la tabla vacía. docker run es create más start en una sola orden.

2. Cuánto tarda docker stop

docker stop manda SIGTERM al proceso número uno del contenedor y espera; si no terminó en diez segundos, manda SIGKILL. Tres contenedores parados, medidos con time:

$docker run -d --name web nginx:alpine ; time docker stop web
$docker run -d --name sordo alpine:3.20 sleep 300 ; time docker stop sordo
$docker run -d --name sordo2 alpine:3.20 sleep 300 ; time docker stop -t 3 sordo2
El proceso sleep 300 no atiende SIGTERM. ¿Cuántos segundos tarda su docker stop?

3. El código 137

Dos de los tres contenedores salieron con 137 y uno con 0. ¿De dónde sale ese 137?

Un servicio en producción tarda siempre exactamente diez segundos en parar. ¿Qué dice ese síntoma?

El plazo existe para que la aplicación cierre transacciones y termine lo que tenía empezado, y solo lo aprovecha si recibe la señal. Para eso el CMD tiene que estar en forma exec, de modo que el programa sea el proceso número uno y no un intérprete de órdenes que no reenvía señales.

4. Borrar lo que todavía corre

$docker rm web
You cannot remove a running container

¿Qué hace docker rm -f web que la orden sin bandera se niega a hacer?

Lo que se escribió dentro del contenedor se pierde al borrarlo, con bandera o sin ella. Para que sobreviva hay que montar un volumen, y eso es lo que se ve en la sesión siguiente.
