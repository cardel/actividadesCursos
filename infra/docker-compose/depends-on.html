depends_on y healthchecks

Una lista de dependencias ordena la creación de los contenedores, y eso no es lo mismo que esperar a que el servicio atienda. Diga qué condición pide cada caso, qué fija cada clave del healthcheck y cuánto tarda la base en quedar marcada como caída.

La base arranca y nunca llega a atender. Contando un sondeo cada interval y los retries que hacen falta, ¿cuántos segundos pasan desde que acaba el start_period hasta que el servicio queda marcado como caído?

Mientras ese estado no cambie, quien declaró condition: service_healthy sigue esperando, y por eso el valor de interval decide lo que tarda el proyecto entero en levantarse.

4. Las dos salidas al problema

La primera salida vive en el YAML: un healthcheck en el servicio y condition: service_healthy en quien depende. La segunda envuelve el arranque en un guion de espera, del tipo wait-for-it.sh, que sondea el puerto antes de lanzar el proceso. ¿Cuándo hace falta la segunda?

1 migrate:
2 image: postgres:16
3 depends_on: { db: { condition: ... } }
4 command: psql -h db -U postgres -d demo -c "CREATE TABLE ..."
5 web:
6 image: nginx:alpine
7 depends_on:
8 db: { condition: ... }
9 migrate: { condition: ... }

La fila de web y migrate es la que se escribe mal con más frecuencia. Un contenedor que corre su orden y sale nunca va a reportarse healthy, de modo que pedirle service_healthy deja al proyecto esperando a algo que ya pasó.
