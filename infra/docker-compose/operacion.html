El ciclo del día a día con Compose

El sistema de la sesión tiene tres servicios: web, que se construye y publica el 8080, db con su volumen pgdata y cache, que no declara ninguno. Las órdenes del ciclo no pesan lo mismo: unas solo miran, otras mueven los contenedores y dos los borran. Lo que decide si un dato reaparece al levantar otra vez es dónde estaba escrito.

1. Las órdenes del ciclo

Cuatro efectos posibles. Solo mira: informa y no cambia nada. Crea y arranca: pone en marcha lo que falte. Para o reinicia: los contenedores siguen existiendo. Borra: el contenedor desaparece y el siguiente arranque hace otro.

De las nueve órdenes, dos borran contenedores y una sola se lleva además los volúmenes. Esa es la que hay que escribir con cuidado.

2. Qué sobrevive a docker compose down

Antes de bajar el sistema se deja una marca en la base: una tabla y dos filas.

$docker compose exec -T db psql -U postgres -d demo \
-c "CREATE TABLE visitas_log (id serial PRIMARY KEY, marca timestamptz DEFAULT now());"

$docker compose exec -T db psql -U postgres -d demo \
-c "INSERT INTO visitas_log DEFAULT VALUES; INSERT INTO visitas_log DEFAULT VALUES;"

$docker compose down
$docker volume ls | grep proyecto

4. El nombre del proyecto

La columna NAME de docker compose ps trae proyecto-cache-1, proyecto-db-1 y proyecto-web-1, y docker volume ls lista el volumen como proyecto_pgdata.

¿De dónde sale el proyecto- de esos tres nombres?

Con ese sistema arriba, en la misma máquina se corre docker compose -p staging up -d sobre el mismo archivo. ¿Qué queda en la máquina?

Si de esa segunda copia se levanta solo la base, con docker compose -p staging up -d db, ¿cuántas líneas devuelve docker volume ls | grep pgdata?

El nombre del proyecto va delante de los contenedores, de la red y de los volúmenes, así que dos copias del mismo archivo conviven sin pisarse los datos. Y por eso un down -v borra el volumen del proyecto en que se corre y no el del otro.
