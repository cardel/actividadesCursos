Swarm: el clúster, manager y worker

El mismo archivo de Compose, ahora sobre varias máquinas. Qué deja fuera Compose plano, qué papel tiene cada nodo del clúster y qué quedó montado después de una sola orden en una sola máquina.

1. Lo que Compose plano deja fuera

Un compose.yml con web, base de datos y caché corre en un servidor, con sus volúmenes y sus healthchecks. ¿Cuál de estas cuatro cosas no la hace Compose?

2. Lo que aporta el clúster

El servicio web corre con tres réplicas en un swarm de tres nodos. Se apaga el nodo donde estaba una de ellas.

Y el archivo de despliegue, ¿qué pasa con él al llevar ese servicio a Swarm?

3. Manager y worker: quién hace qué

Los managers mantienen el estado del clúster con Raft y los workers ejecutan las tareas que les asigna el líder. Diga de quién es cada responsabilidad.

ResponsabilidadDe quiénRespuesta
El plano de control no se reparte: lo sostienen los managers y nada más. Ejecutar tareas sí se comparte, y por eso un manager con el rol both corre réplicas como cualquier worker. De ahí que un swarm de un solo nodo pueda servir un servicio.

4. docker swarm init en una sola máquina

$docker swarm init
Swarm initialized: current node (ibherjfz80z5j0k4ht3skp6i0) is now a manager.
docker swarm join --token SWMTKN-1-4vzt1fmxpd9mtgaiv3r7l4kyg2[...]0zsjoqh4ruu1dtfsqpnbh662z 192.168.18.52:2377
$docker node ls
ID HOSTNAME STATUS AVAILABILITY MANAGER STATUS ENGINE VERSION
ibherjfz80z5j0k4ht3skp6i0 * cardel-desktop Ready Active Leader 29.7.2

Hay un solo nodo y ya aparece como Leader. ¿Qué significa eso?

El comando de unión trae 192.168.18.52:2377 y nadie pasó --advertise-addr. ¿De dónde salió esa dirección?

Se unen dos managers más y, tiempo después, este nodo cambia de dirección. ¿Qué se ve en docker node ls?

Lo que dejó la orden se puede leer de un tirón: docker info con un formato propio contesta Managers=1 Nodes=1 Estado=active PlanoDeControl=true. Un clúster de un solo nodo ya es un clúster.

4. Para resolver en la máquina

Inicie un clúster de un solo nodo, levante un servicio de una réplica y mire qué informa docker node ls sobre ese nodo. Saque después el nodo del clúster con docker swarm leave --force y diga qué pasó con el servicio y quién tendría que haberlo reprogramado.
