De docker run a un compose.yml

Cinco órdenes levantan la aplicación de tres piezas, en un orden que no está escrito en ninguna parte. El mismo sistema cabe en un archivo. Diga qué clave recoge cada bandera, qué dice la columna de puertos y qué prueba cada dato de las dos peticiones.

1. De cada bandera a su clave

$docker network create app-net
$docker volume create pgdata
$docker run -d --name db --network app-net \
-e POSTGRES_PASSWORD=ejemplo -v pgdata:/var/lib/postgresql/data postgres:16
$docker run -d --name cache --network app-net redis:7-alpine
$docker run -d --name web --network app-net -p 8080:5000 \
-e DB_HOST=db -e DB_PASSWORD=ejemplo mi-app:1.0

Para cada pieza de esas órdenes, elija la clave del compose.yml que la recoge.

En la ordenClaveDónde queda
El archivo queda en la carpeta del proyecto y todas sus rutas se resuelven desde ahí, de modo que build: ./app apunta a la carpeta con el Dockerfile.

2. El contador de las dos peticiones

$docker compose up -d --build
$curl -s localhost:8080
{"db_ok":true,"visitas":1}
$curl -s localhost:8080

El endpoint hace cache.incr("visitas") y devuelve el valor. ¿Qué trae visitas en la segunda petición?

$docker compose down
$docker compose up -d
$curl -s localhost:8080

Y después de bajar y volver a levantar el sistema, ¿con qué valor contesta?

La tabla visitas_log de PostgreSQL sí conserva sus dos filas tras el down, porque la base monta el volumen pgdata y docker volume ls lo sigue listando.

3. La columna de puertos de docker compose ps

$docker compose ps --format 'table {{.Service}}\t{{.Status}}\t{{.Ports}}'
SERVICE STATUS PORTS
cache Up 14 seconds 6379/tcp
db Up 14 seconds 5432/tcp
web Up 14 seconds 0.0.0.0:8080->5000/tcp, [::]:8080->5000/tcp

cache y db aparecen sin dirección delante del puerto. ¿Por qué?

Entonces, ¿quién alcanza el 5432 de la base?

4. Qué prueba cada dato

$curl -s localhost:8080
{"db_ok":true,"visitas":1}
$curl -s localhost:8080
{"db_ok":true,"visitas":2}
$docker compose logs --tail 3 web
web-1 | * Running on http://127.0.0.1:5000
web-1 | * Running on http://172.19.0.4:5000
web-1 | 172.19.0.1 - - [09/Sep/2026 00:57:39] "GET / HTTP/1.1" 200 -

Cada dato de ahí demuestra una cosa distinta. Empareje.

DatoQué demuestraRespuesta
Las dos direcciones del log son de la misma red y no dicen lo mismo. 172.19.0.4 es la del contenedor de web, donde Flask quedó escuchando; 172.19.0.1 es la puerta de enlace, y por ahí entra todo lo que viene del anfitrión.
